# Security triage capability — handoff to flyto-code and flyto-engine

Owner: claude
Branch: main
Date: 2026-08-19

This is a capability + discipline handoff for the future owners of `flyto-code`
(user-facing security/CTEM/redteam/reporting workspace) and `flyto-engine`
(evidence-backed backend state). It hands off **both** the taint/triage
capability now in `flyto-indexer` **and** the discipline that must govern any
"find → fix → submit" product built on top of it. Inherit both, not just the
first.

## What the capability is

A local, zero-dependency security-research **triage** layer inside
`flyto-indexer`. It narrows a whole repository to a short, ranked reading list
of code paths worth a human's time, and says what it did not check.

Pieces (all shipped to `flyto-indexer` main this session, CI green):

- **Taint engine** (`src/analyzer/taint.py`) — AST, pure stdlib. Sources /
  sinks / sanitizers / **propagators**, all configurable via `.flyto-rules.yaml`
  (`taint.*`). This session added: return-value taint with a global fixpoint,
  field sensitivity for `self` attributes across methods, sinks inside
  `with` / `async with`, method-form Flask sources, and mutation propagators
  (`parse_dict`, `list.append`, `d[k]=`, `MergeFrom`).
- **Ranking** (`src/analyzer/research_priority.py`, tool `research_priority`,
  CLI `research-priority`) — fuses taint reachability, sink severity,
  entry-point exposure, complexity, git churn, test gaps, error handling into
  one ordered list with labelled evidence tiers. Demotes demo/example/script
  code and operator-fed flows; never drops a proven flow silently.
- **Selective LSP verification** — `call_hierarchy` resolves cross-function
  attribution type-aware, used on the shortlist only.
- **Orchestration skill** — `skills/security-triage/SKILL.md`. A budget-aware
  funnel over the existing tools: proven flows first, ranked leads, LSP on the
  top ~8 only, then a human reading list. No new tool, no dependency.

## How flyto-code / flyto-engine consume it

- `flyto-engine` already has an export path (`flyto-index export`) that bundles
  scan results for upload. The ranking output (candidates + evidence tiers +
  coverage) maps cleanly onto engine's evidence-backed state model: each
  candidate is a finding with a **confidence tier**, not a verdict.
- `flyto-code` renders the reading list. The important UI contract: show the
  **evidence tier** (`proven_flow_*` vs the unproven tiers) and the
  `coverage.signals_unavailable` block. The product's honesty is the
  differentiator; hiding "what wasn't checked" would throw it away.
- Neither should treat a candidate as a confirmed vulnerability. The engine
  finds *paths*; a human finds *bugs*.

## Honest strength / limit (do not let this drift in the pitch)

- **Strong at:** speed (21s clone→ranked-leads on 117k lines), honest signal
  fusion, lean zero-dep engineering, orchestration.
- **Mid at:** raw cross-function taint recall. It is name-based across
  functions; whole-program, type-resolved dataflow (CodeQL / Pysa) finds more.
  Measured: gradio 4 proven flows, mlflow 1. A large repo yielding few proven
  flows is the honest floor, not a clean bill of health.
- **The positioning that survives contact with a security expert:** *not a
  stronger scanner — a faster, more honest triage that narrows the codebase and
  says what it skipped. The human brings the judgment.* This does not break
  when someone runs it on mlflow and sees one flow.

## The "connect GitHub → clone others' repos → fix → submit PR" idea

The capability is buildable on `flyto-ai`'s already-audit-gated coding pipeline
(Indexer + Blueprint + Core lanes). But the **same action builds or destroys
reputation depending entirely on volume, verification, and disclosure**. Treat
the following as hard requirements, not options — they are the reason the
product is reputation-positive instead of another AI-slop bot:

1. **Never auto-submit an unverified finding.** The engine's unproven tiers are
   leads, not bugs. A fix PR requires a confirmed, reproduced issue. gradio's
   own SECURITY.md closes "auto-generated by a scanner or LLM" reports without
   review — an unverified-PR bot is dead on arrival and burns the name.
2. **Security fixes go through coordinated private disclosure, never a public
   PR first.** A public PR that "fixes a security bug" broadcasts the
   vulnerability before a fix ships. Use the project's security policy /
   private advisory; open the PR only when the maintainer agrees.
3. **Volume is inverted from intuition.** A few verified, PoC-backed, well-
   disclosed findings build far more reputation than mass auto-PRs. Keep the
   human-confirm gate; do not remove it to scale.
4. **A wrong auto-fix merged by a trusting maintainer is a real harm.** Fixes
   need review and tests, not just generation.

The template already exists in this session's work: the gradio `undo_vibe_edit`
path traversal was found by triage, **confirmed with a PoC on a released
version**, and routed to a private advisory draft — not auto-PR'd. That is the
shape that builds a name. (Note: its details were briefly committed to a public
repo and then redacted; git history retains them. Do not repeat that — verify
the disclosure path before anything is written down publicly.)

## Future feature spec — human-gated disclosure export (flyto-code)

Not urgent; the owners are on bug-fixing. Captured so it can be built without
re-deriving. This is the **human-driven** product the owner intends — a force
multiplier for manual scanning, never an autonomous bot. Every step passes
through a person.

**The loop (each arrow is a human action or a human-gated one):**

1. Human picks and clones a target repo (deliberate, one at a time — not mass
   auto-clone).
2. `flyto-index scan` + the `security-triage` skill produce the ranked reading
   list.
3. Human researches the top candidates as they normally would; confirms or
   drops each. Only a **human-confirmed, reproduced** finding proceeds.
4. AI summarizes the confirmed finding into a disclosure-shaped draft — this
   session already did it by hand: it read the target's `SECURITY.md`, filled
   the required template (summary / affected version / component / class /
   vector / **PoC** / impact / suggested fix), and produced a GHSA-ready
   advisory. Make that a repeatable **export**.
5. Human reviews the draft and **clicks to file** (or not). The tool never
   sends; it prepares. Route is the project's private channel (GitHub private
   advisory / security email), never a public PR or issue first.

**Where it lives:** `flyto-code` (it already owns reporting + evidence). The
export reads the confirmed finding + the target's SECURITY.md template and
emits the advisory; `flyto-engine` stores it as evidence state with a
`disclosed?` flag. `flyto-indexer` is untouched — it stays the triage tool.

**Hard rules baked into the export (these are what keep it reputation-positive):**

- The draft is built only from real evidence and a real PoC. No fabricated
  proof, no inflated impact. If there is no PoC, it is not exportable as a
  report — it stays a lead.
- "File" is a deliberate human click, defaulting to off. The system prepares;
  the person discloses.
- Coordinated/private first. A public PR only after the maintainer agrees.
- Reference template: this session's `undo_vibe_edit` advisory (verified PoC on
  gradio 6.24.0, followed gradio's required structure). That is the shape the
  export should reproduce.
